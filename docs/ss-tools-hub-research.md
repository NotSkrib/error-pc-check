# SS Tools Hub Research

**Reviewed:** 2026-09-30
**Source:** [SSToolsHub.ps1](https://raw.githubusercontent.com/3ntrsquad/SSToolsHub/refs/heads/main/SSToolsHub.ps1) (`refs/heads/main`, mutable)

**Linked-repository follow-up:** selected upstream GitHub repositories opened on 2026-09-30; scope below prioritizes code-bearing repositories named by scanner behavior or linked executables. README claims are attributed as claims, not independently validated test results. This is not an audit of all 83 binaries, every one of the 44 remote scripts, nor every catalog publisher.

**Additional follow-up:** reviewed further project pages and script repositories listed in the hub, especially screenshare collectors, registry/macro checks, journal readers, client analyzers and forensic collectors. Remote scripts were reviewed as source/documentation only, not run.

## Scope and method

The linked PowerShell file was fetched and inspected as text only. It was **not executed**. None of its download entries, remote scripts, commands, installers, or scanner subprocesses were run. This is a static review of the hub's current source, not a security audit of third-party binaries or scripts; the branch URL can change after this review.

The hub is a Windows WPF launcher/catalog, not a single scanner engine. It defines separate tool, script, and command catalogs and dispatches clicks to download/install, run, open, or scan actions. Labels and URLs are not proof of the behavior or safety of the payloads they point to.

## Hub mechanics and trust boundaries

- **Downloaded tools:** the catalog contains 83 entries across 17 categories (NirSoft, EricZimmerman, Spokwn, Echo, OrbDiff, RedLotus, TRSSCommunity, Magnet, Forensics, SystemTools, Analysis, Misc, Meow, Praiselily, TeslaPro, Xeinn, Dependencies). They include Prefetch, BAM, UserAssist, USB, USN/journal, registry, shell history, Amcache, MFT, SRUM, timeline, process, JAR, macro, injection/decompiler, disk/RAM imaging and system-monitor utilities, as well as runtimes and installers. The hub generally downloads EXE/JAR/ZIP payloads from URLs in the catalog and extracts archives; this review did not inspect or validate every payload. Several URLs are mutable `latest`/branch/raw links.
- **Scripts:** 44 entries include registry and macro checks, JAR/mod scanners, service and directory tools, BAM/USN/recycle-bin/USB/history utilities, client-specific detectors, collectors, an AnyDesk installer and local scanner wrappers. Duplicate names/entries exist. Most remote entries point at raw GitHub branch heads or Pastebin; the dispatch path launches scripts with PowerShell execution-policy bypass. DQRKIS explicitly builds a command that downloads a raw script and pipes it to `Invoke-Expression`. That is arbitrary remote code execution and is not suitable for reuse as an implementation pattern.
- **Commands:** 60 catalog entries open shell folders and Windows management tools or launch command-line diagnostics (including continuous ping, DNS flush, SFC/DISM, `bcdedit`, network/process/service inventories). Some are observational; some mutate system state or run indefinitely. They are actions, not validated scanner tests.
- **Download behavior:** catalog URLs are used to retrieve executable content without a pinned digest/signature verification step visible in the hub flow. A ZIP is extracted before the UI reveals its location. A JournalTrace path separately downloads an EXE to a temporary location and launches it. Treat these as untrusted supply-chain inputs until independently verified.
- **Local PowerShell scanners:** the six embedded scanner families are extracted/launched as temporary PowerShell scripts with `-ExecutionPolicy Bypass`; their content is inspectable in the hub file, but that does not make execution a safe or necessary integration choice.

## Fit with this repository

The C# client already implements consent-scoped process, Prefetch, BAM, UserAssist, ShimCache, registry, recycle-bin, PowerShell-history, Minecraft instance/JAR/manifest/log/config, USN, event-log and correlation modules. `MinecraftLocator` identifies common launcher instances; `MinecraftModule` reads `mods/*.jar` names and bounded ZIP entries (plus selected metadata), manifests, logs and configs, and applies the local versioned signature DB. Browser-download inspection exists as a separately described module. Amcache/MFT are explicitly not implemented yet.

This is a better base than importing the hub's one-off scripts. Existing modules are human-review evidence collection; no scanner should silently change settings, install tools, run third-party scripts, upload hashes to lookup services, or expand into entire drives.

### Binaries or claims not independently audited

Many catalog repositories either link straight to an EXE or release asset, have README-only descriptions, or point to mutable “latest” artifacts. A public repository containing some source does **not** prove its distributed binary was built from that source. The hub also lists commercial/vendor download links (NirSoft, Magnet, AccessData/FTK, Velociraptor and others); their behavior must be reviewed at their own authoritative documentation/release and license level before bundling or automating. We did not download or execute those programs.

Other script links in the 44-entry list were not all reviewed line-by-line in this follow-up. They include TR community auto-downloaders, faker/hotspot checks, additional JAR/mod analyzers (Habibi/Yumniko/Yarp), common-directory and service scripts, hard-disk conversion, injector/VPN/macro/client detectors, Pastebin-hosted security/quick-check scripts, DQRKIS, and generic macro detection. Until each exact file is reviewed at a pinned revision, its actual behavior, scope and side effects are unknown; catalog labels are not enough to describe implementation. The `IEX` + mutable raw-branch pattern recurs in project README examples and is a supply-chain risk independent of whether a particular current revision appears benign.

Among the selected repositories, specific privacy/behavior findings from source and README review include:

- MeowModAnalyzer advertises third-party SHA-1 lookups, reading download-source streams, deep archive inspection, and runtime/JVM checks. Treat hash lookup as data disclosure even when no file bytes are uploaded.
- MeowDoomsdayFucker and MeowClientFucker describe live Java memory reads; MeowClientFucker additionally describes DNS-cache checks. These require explicit user awareness and a much higher trust bar than on-disk collection.
- MeowResolver offers automatic registry/system remediation, which is outside a forensic collector's read-only purpose.
- JournalTrace advertises GPL-3.0; its code and credited dependencies cannot simply be copied into this product without license review.
- BAM/Prefetch/Amcache tools rely on generic/YARA-like detection sets and path/replacement correlation. Their authors acknowledge false positives; use matched artifacts as evidence for a human, not as an automatic guilt verdict.
- The Prism repo's disclosed scope spans game data and broad user folders plus system artifacts; its `-Paranoia` option and Desktop report should be treated as higher-collection modes, not assumed defaults for this app.
- The Prism source's consent prompt can be bypassed with `-SkipConsent`; its signature weights are heuristic points rather than calibrated confidence. Never infer a probability or guilt verdict from its score.
- The RedLotus Collector adds a Defender exclusion, downloads/unpacks a ZIP and launches an executable. Treat it as high risk, state-changing bootstrap code, not a forensic collector.
- TeslaProMacroFinder's optional `-Deep` mode scans all filesystem drives for selected names/extensions and writes report files next to the script; ordinary vendor/process/config matches still do not prove macro use.
- Collection repositories may redistribute scripts authored by others. Verify the original author, exact revision, license, and output behavior for each file instead of inheriting a bundle's name or trust.

The concrete follow-up for implementation remains local and small: renamed archive-header triage in already-discovered Minecraft `mods/` directories. Deeper jar heuristics, memory scans, archive decompilation, hash lookups, automatic repairs and copied third-party parsers stay out pending focused implementation and test plans.

## Implemented from this review

`MinecraftModule` now has two bounded archive checks: **renamed-JAR triage** within already-discovered launcher `mods/` folders (first four bytes of non-`.jar` files must match ZIP/JAR `PK\x03\x04`, Low severity, lead-only wording, 3,000-file aggregate cap), and **nested-JAR metadata scanning** for `META-INF/jars/*.jar` entries in scanned mods. Nested inspection is in-memory only, limited to 4 MiB per nested archive, 128 nested archives and 64 MiB declared uncompressed nested content per whole scan. It reads only selected metadata entries (e.g. `fabric.mod.json`, `mods.toml`, manifests and mixin JSON) and feeds them to the existing signature matcher; it does not decompile, recurse into further nested JARs, extract to disk, or execute content.

There are no new network calls and no archive extraction to disk. The scanner does not execute candidate content. No external tool or script was added to the product.

## Implementation and test plan

1. Reuse `MinecraftLocator.Instances()` and enumerate only direct files in each discovered instance's `mods/` directory, as the existing JAR pass does. Do not add Downloads/Desktop/Temp or drive-root recursion.
2. Bound the new pass to 3,000 direct files total across instances; cap inspected header reads to four bytes per candidate. Skip `.jar` extensions and handle locked/missing files as the rest of the module does.
3. Require ZIP local-file magic bytes `50 4B 03 04`; do not infer a JAR from extension, filename words or a partial signature. Emit Low severity, scoped evidence and neutral wording; do not count this as a known-cheat signature or execution event.
4. Unit-test a valid ZIP/JAR header with a misleading extension, a non-ZIP file, a `.jar` file (not duplicated), a missing/locked candidate, and scope/budget behavior. Add only synthetic temp fixtures; never inspect the developer's actual profile in unit tests.
5. Build the .NET client after changes. Run tests only when explicitly asked to verify behavior; don't invoke the hub or real scanner payloads as a test.

## Recommended handling of remaining hub ideas

- Prefer existing local Prefetch/USN/BAM/registry modules over third-party parser downloads.
- If Amcache/MFT support is later needed, use a maintained parser/library after license, parser-hardening and fixture review; keep it opt-in/elevated and evidence-only.
- Keep remote reputation lookups off by default. If ever introduced, disclose exact fields, destination, retention and failure behavior and get explicit consent.
- Treat client-name/module strings as weak indicators. Require independent corroboration and present provenance/confidence rather than claiming guilt.
- Never run mutable remote scripts with `IEX`, bypass execution policy, or auto-launch downloaded binaries. If the product ever distributes tools, pin versions and hashes/signatures, show publisher/source, verify before extraction/run, and make launch an explicit user action.
